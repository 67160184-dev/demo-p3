ฟีเจอร์ที่เพิ่มใน Phase 3 (login admin, ค้นหา/กรองสินค้า, แก้ไขสินค้า/หมวดหมู่/ผู้จัดจำหน่าย, ลบ, ดูรายละเอียดหมวดหมู่/ผู้จัดจำหน่าย และแสดงราคาทุกแถวเป็นสกุลเงินเดียวกัน) เพื่อให้ผู้ดูแลจัดการข้อมูลได้เองจากหน้าเว็บอย่างปลอดภัย — ใช้ foreign key เดิมใน `schema.sql` (ลบหมวดหมู่ = CASCADE ลบสินค้าในหมวด, ลบผู้จัดจำหน่าย = SET NULL); ตัวเลือกหมวดหมู่/ผู้จัดจำหน่ายในฟอร์มสินค้าดึงจาก API จริง (เดิมใช้ค่าตายตัว + `localStorage` เพราะไม่มี API รายการ)

ตรวจจริงว่า 3 ระยะเป็นระบบเดียวกัน (เทียบไฟล์ด้วย `diff`):
- `db.js`, `schema.sql` และ `seed.sql` อยู่ระดับบนตามรูปแบบการส่งล่าสุด; ตาราง `categories`, `suppliers`, `products` และข้อมูลตั้งต้น 3+3+3 รายการสืบต่อจาก Phase 1 ส่วน Phase 3 เพิ่มตาราง `users` กับบัญชี admin และให้ `seed.sql` ตั้งรหัสกลับเป็นค่าเริ่มต้นเมื่อล้างข้อมูล
- route ของ Phase 1 ทั้ง 7 รายการยังอยู่ครบ (path/HTTP method เดิม) บวก `GET /products/:id/price` ของ Phase 2, route จัดการข้อมูล 7 รายการ (DELETE สินค้า/หมวดหมู่/ผู้จัดจำหน่าย, GET และ PATCH หมวดหมู่/ผู้จัดจำหน่าย) และ route login/บัญชี 3 รายการ (login, me, change-password) ที่เพิ่มใน Phase 3
- `src/services/external-api.js` ใช้แนวทาง retry/timeout/fallback ต่อจาก Phase 2; `openapi.yaml` ต่อยอดจาก Phase 2 โดยเพิ่ม 10 operation ใหม่, `securitySchemes.bearerAuth` และคำตอบ 401/403 ของ route ที่ต้องเป็น admin, และปรับ PATCH สินค้าให้ตรงพฤติกรรมใหม่
- `src/index.js` ต่างจาก Phase 2: `require("../db")` (ตามตำแหน่งใหม่), ไม่พิมพ์ log ของ morgan ตอนรัน test, `express.static` เสิร์ฟหน้าเว็บ (ไม่ใช่ API endpoint จึงไม่อยู่ใน spec), `module.exports = app` + `listen` เฉพาะตอนรันตรง เพื่อให้ Supertest ทดสอบได้, เพิ่ม route login/me/change-password + 7 route จัดการข้อมูล, POST/PATCH/DELETE ทุกตัวต้องเป็น admin (`requireAdmin`), GET สินค้าส่ง `category_id`/`supplier_id` เพิ่ม และ PATCH สินค้ารับเฉพาะช่องที่ส่งมา (`name`, `sku`, `price`, `stock_quantity`, `category_id`, `supplier_id` — ไม่ส่งเลยตอบ 400) — **client เดิมของ Phase 2 ต้องแนบ token ของ admin ตอนเรียก POST/PATCH/DELETE แล้ว** (ไม่แนบได้ 401)

## ผลออกแบบ Microservices จากสัปดาห์ที่ 13 ที่รวมเข้าระยะที่ 3

ใบงานสัปดาห์ที่ 13 ส่วนที่ 3.2 กำหนดให้ "ออกแบบ (ไม่จำเป็นต้องแยกโค้ดจริงทั้งหมด)" จึงสรุปผลออกแบบไว้ที่นี่ และโยงกับโค้ดจริงของระบบรวม:

| บริการที่ออกแบบ (Bounded Context) | ความรับผิดชอบ | อยู่ตรงไหนในโค้ดปัจจุบัน (Monolith) |
| --- | --- | --- |
| Category Service + `category_db` | จัดการหมวดหมู่ | route `/api/v1/categories...` ([src/index.js:309-377](src/index.js)) |
| Supplier Service + `supplier_db` | จัดการผู้จัดจำหน่าย | route `/api/v1/suppliers...` ([src/index.js:380-461](src/index.js)) |
| Product Service + `product_db` | จัดการสินค้า/สต็อก + แปลงราคาผ่าน API ภายนอก | route `/api/v1/products...` ([src/index.js:112-306](src/index.js)) + [src/services/external-api.js](src/services/external-api.js) |
| API Gateway | auth ส่วนกลาง + routing | ยังไม่แยกเป็นบริการ — ตอนนี้ auth อยู่ใน process เดียวกัน ([src/middlewares/auth.js](src/middlewares/auth.js)) ซึ่งเป็นโค้ดที่ย้ายไปไว้ที่ Gateway ได้ตรงๆ เมื่อแยกบริการ |

- การสื่อสารระหว่างบริการออกแบบเป็น Synchronous ทั้งหมด เพราะสต็อกต้องถูกต้องแบบ real-time (เช่น ต้องรู้ทันทีว่า `category_id` มีจริงก่อนบันทึกสินค้า)
- จุด resilience ที่ออกแบบไว้: Product Service → External Currency API ต้องมี Retry + Timeout + Fallback — **จุดนี้มีโค้ดจริงและ test จริงแล้ว** (`external-api.js` + `external-api.test.js`); Product → Category ต้องมี Timeout (ตอบ 503 เมื่อช้า), Product → Supplier มี Timeout + Fallback (บันทึกโดย `supplier_id = NULL` ได้ เพราะ schema อนุญาต), Gateway → ทุกบริการตอบ 503 ที่มีความหมายเมื่อบริการปลายทางล่ม
- เหตุผลที่ระยะที่ 3 ยังไม่แยกบริการจริง: ข้อมูลยังเล็ก ระบบเดียวดูแลง่ายกว่า และการแยกฐานข้อมูลจะทำให้ query JOIN ของ UC-04 ต้องเปลี่ยนเป็นการเรียกข้ามบริการ — แผนภาพและตารางฉบับเต็มอยู่ในใบงานสัปดาห์ที่ 13 (`microservices-design.md`)
